# ToddleGo 架构与方法评审（2026-10）

> 背景：恢复开发后，第一次跑通"抓取 → Gemini 解析 → Firestore → App"全链路。本文基于这次运行的真实数据，回答两个问题：
> 1. 扩展到全加州、全美国时，费用和架构怎么撑住？
> 2. 相对 Eventbrite 和 funradar，ToddleGo 的优势在哪里？

## 结论

1. **成本的根源不在"用了 LLM"，而在"用 LLM 读整个网页"这种方法。** 改成按日历平台写结构化适配器后，覆盖全美的边际成本可以接近零。
2. **规模化后真正的成本风险在客户端读取，而不在爬虫。**
3. **离"最全"最近的一步是修事件 ID 冲突 bug。** 实测它让每周重复的活动丢掉约 45%（见第三节第 1 条）。

## 一、用 2026-10-10 那次运行的数据校准费用

三个任务大约花了 $1，生成 114 条活动，平均约 $0.01 一条。但各来源的产出率差别很大：

| 来源 | Gemini 调用 | 新增活动 | 问题 |
|---|---|---|---|
| City Calendar（活动日历页） | 17 | 73 | 产出率还可以 |
| Library（`url_registry`） | 37 | 10 | 大部分是图书馆首页，不是日历页 |
| Serper（搜索摘要） | 8 + 40 次搜索 | 31 | 依据只是搜索摘要，真实性最弱 |

浪费集中在两处：
- 把整页（截取前 80k 字符）交给 LLM 去"找活动"。
- 发现阶段注册了大量不是活动页的网址，比如图书馆首页和公园官网。

按现在的方法扩展到全美，LLM 花费大约是每周几百美元（粗估）。这笔钱本身不致命，**致命的是产出率低、错误多，而且无法验证。**

## 二、方法转变：从"网页 → LLM"到"平台适配器"

图书馆的活动日历集中在少数几个 SaaS 平台上。从现有来源列表就能看到：

- **BiblioCommons**：aclibrary、sjpl、smcl、marin、ccclib
- **LibraryMarket**：hayward.librarycalendar.com
- 其他常见平台：Springshare LibCal、Communico 等

这些平台大多有结构化的数据出口，比如 iCal、RSS 或 JSON。**每个平台的具体接口和服务条款都需要逐个核实，目前还没有验证。**

| | 现在：网页 → LLM | 平台适配器 |
|---|---|---|
| 每条活动的 LLM 成本 | 有，而且大量花在没有活动的页面上 | $0（确定性解析） |
| 覆盖面 | 一个网址对应一个来源 | 一个适配器覆盖使用该平台的所有图书馆系统 |
| 准确性 | 依赖模型，可能编造 | 直接使用平台原始字段 |
| 活动 ID | 自己拼接（有冲突 bug） | 平台原生 ID |
| 取消或改期 | 很难发现 | 和上次数据对比就能发现 |

LLM 只保留两种用途：
- 没有结构化接口的长尾网站。
- 对单条活动的短文本做补充，比如判断适合的年龄、是否适合幼儿。结果按单条活动的内容哈希缓存，同一条活动只付一次费。

**商业化前提**：逐个确认这些平台的服务条款和 robots.txt 是否允许使用它们的数据。

## 三、架构改进清单

### 1. 修事件 ID 冲突（P0）

[`generateEventId`](../functions/utils/helpers.js) 先对 "title-venue-date" 做 base64 编码，再截断到 50 个字符。50 个 base64 字符只能覆盖原字符串的前 37 个字符，**日期被截掉了**。结果是，同一个场馆同一个标题的每周活动（比如 Dublin 分馆的 Baby Bounce）在不同日期得到同一个 ID，只有第一场能写进数据库。

**实测**：用缓存的解析结果去重，旧 ID 得到 59 条不同的活动，按标题 + 场馆 + 日期去重是 108 条，**丢了约 45%**。

**修法**：
- 有平台活动 ID 时，用"来源 + 平台活动 ID"作为 ID。
- 没有时，对完整的"标题 + 场馆 + 日期 + 时间"做 SHA-256 哈希，不再截断。

### 2. 来源清单：不再用 Places API 去"发现"

[`discoverCaliforniaLibraries`](../functions/jobs/discoverCaliforniaLibraries.js) 一次大约 $15，找到的多半是首页。

改用美国 IMLS 每年发布的 Public Libraries Survey 数据。它免费覆盖全美约 17,000 个图书馆分馆，据了解带经纬度（**待核实**）。在它上面建一张"来源表"，每条记录是：分馆、所属系统、使用的日历平台、平台上的租户 ID。之后扩展到新地区，主要工作就是往这张表里加数据。

### 3. 数据模型：场馆实体和重复活动系列

- **场馆实体**：现在每条活动都拿场馆名称的文本去做地理编码，名称写法稍有不同就重复付费。改为独立的场馆记录，坐标固定，活动只引用场馆 ID。
- **重复活动系列**：幼儿活动大多是每周固定的 storytime。建模为"系列 + 重复规则（RRULE）"，不要每场单独抽取。这样也能做出"每周固定时间表"视图，竞品没有。

### 4. 客户端查询：规模化后最大的成本风险

[`_activitiesTodayAndFuture`](../lib/main.dart) 会实时订阅**全部**未来活动，再在手机上按距离筛选。

- Firestore 按读取的文档数计费，大约每 10 万次读取 $0.03–0.06。
- 如果全美有 10 万条未来活动，每打开一次 App 约 $0.03–0.06。按 1 万日活、每人每天打开 2 次算，**每天 $600–1,200**。
- **修法**：数据里已经存了 `geohash`，按 geohash 范围查询，再加时间窗口和分页，每次只读几百条。实时订阅改为普通的一次性查询。

### 5. 流水线和监控

这次数据断了好几个月：定时任务一直暂停，Gemini 2.0 停用后每次调用都失败，但都没有告警。

- **按来源拆分任务**：从一个函数串行处理所有来源，改成每个来源一个任务（Cloud Tasks 队列）。任务可以安全地重复执行、失败了自动重试，并记录每个来源的健康状况：上次成功时间、产出数量、错误率。
- **数据新鲜度告警**：比如某地区未来 7 天的活动数低于阈值，或某个来源连续 2 次产出为 0，就发告警。

## 四、竞争定位

| | Eventbrite | funradar | ToddleGo 的机会 |
|---|---|---|---|
| 核心内容 | 主办方自己发布、多数要买票的商业活动 | 按它自己的介绍：约 4,000+ 个**地点**（游乐场、公园、图书馆、博物馆、海滩）加周末活动，以地图为主 | **公共机构的免费、每周固定活动**，按场次具体到时间 |
| 图书馆 storytime | 基本没有 | 部分有（条目 ID `scraped-bc-paloalto` 暗示它也在抓 BiblioCommons，这只是推测） | 可以接近全覆盖 |
| 粒度 | 单个活动 | 地点为主 | 场次、年龄段、时间段 |

注：funradar 的页面是 JavaScript 渲染的，以上信息只来自它的公开元数据，没有实际使用过。

**优势只有在三点同时成立时才算数：**

1. **覆盖更全，并且有来源可查**：每条活动附原始链接和"最后核实时间"，取消或改期能检测出来。这就是"最真实"的具体含义。
2. **为幼儿家长的决策方式做设计**：比如"今天上午、开车 15 分钟内、适合 2 岁、免费"，能结合午睡时间筛选，或者生成"每周固定时间表"。funradar 回答的是"去哪儿"，ToddleGo 回答的是"现在、这周做什么"。
3. **数据持续新鲜**：依赖第三节第 5 条的监控。

"最全"本身不构成护城河，用户感受不到"全"，只能感受到"每次打开都能找到今天能去的活动"。

**商业化**：用了适配器后，数据的边际成本很低，成本不再是瓶颈。收入方向可以考虑：
- 幼儿课程商家（音乐课、体操馆等）的付费推广位。
- 订阅功能：提醒、日历同步、家庭共享。
- 把数据卖给育儿类 App 或图书馆联盟。

## 五、建议的先后顺序

1. **修 ID 冲突 bug**：改动小，能立刻提升覆盖率。
2. **验证 2–3 个平台的结构化接口和服务条款**，按影响面依次是 BiblioCommons、LibraryMarket、LibCal。可行的话，先用适配器替换湾区的来源。
3. **改造客户端查询**：在用户量上来之前完成。
4. **加上监控和告警**，然后再扩展到全加州。
